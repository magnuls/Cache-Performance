HOW TO MEASURE CPU CACHE PERFORMANCE
====================================
A plan for writing a simple C++ benchmark (src/main.cpp) that reveals the
behavior of your CPU's cache hierarchy (L1 / L2 / L3 / main memory).
No code here — just the approach.


1. THE CORE IDEA
----------------
Memory access speed depends on WHERE the data lives. If your working set
fits in L1 cache, reads take ~1 ns. If it only fits in main memory, reads
take ~60-100 ns. By timing the same access pattern over arrays of
increasing size, you can watch the latency jump each time the array
outgrows a cache level. Those jumps ARE your cache sizes.


2. KNOW YOUR HARDWARE FIRST
---------------------------
On macOS, find your actual cache sizes so you can predict where the jumps
should appear:

    sysctl hw.l1dcachesize hw.l2cachesize hw.l3cachesize
    sysctl hw.cachelinesize

Write these numbers down. On Apple Silicon note that performance cores and
efficiency cores have different cache sizes, and there may be no L3
(there is a system-level cache instead).


3. EXPERIMENT A: WORKING-SET SIZE SWEEP (cache size detection)
--------------------------------------------------------------
- Allocate an array of N bytes.
- Repeatedly access elements in it (see step 5 for how) a fixed total
  number of times, e.g. 100 million accesses regardless of N.
- Time the whole loop; divide by the access count to get ns/access.
- Repeat for N = 4 KB, 8 KB, 16 KB, ... doubling up to ~256 MB.
- Plot ns/access vs. N (log scale on the x-axis).

Expected result: a staircase. Flat plateaus while N fits in a cache
level, a step up each time N exceeds L1, then L2, then L3.


4. EXPERIMENT B: STRIDE SWEEP (cache line size detection)
---------------------------------------------------------
- Use one large array (much bigger than the last-level cache, e.g. 256 MB).
- Access every k-th byte, for stride k = 1, 2, 4, 8, ... 1024.
- Time ns/access for each stride.

Expected result: time per access rises with stride until the stride
reaches the cache line size (typically 64 or 128 bytes), then flattens.
Once each access touches a different cache line, going further apart
can't make it worse — that knee is your line size.


5. DEFEAT THE PREFETCHER: POINTER CHASING
-----------------------------------------
Modern CPUs prefetch predictable (sequential/strided) access patterns,
which hides the latency you're trying to measure. The standard trick:

- Make the array an array of indices, where each element stores the
  index of the NEXT element to visit (a linked list embedded in an array).
- Shuffle the chain into a random permutation (one single cycle through
  all elements, so you visit each exactly once per lap).
- The benchmark loop is just: index = array[index], repeated millions
  of times. Each load depends on the previous one, so the CPU cannot
  overlap or predict them. This measures true latency.

Compare random-order chasing vs. sequential access on the same sizes —
the gap between the two curves shows you what prefetching buys.


6. MEASUREMENT HYGIENE (this is where benchmarks go wrong)
----------------------------------------------------------
- Compile with optimizations ON (the CMake file here defaults to Release).
- Prevent the compiler from deleting your loop: accumulate a result
  (e.g. the final index) into a volatile variable or print it at the end.
- Warm up: run the loop once untimed before the timed run, so the first
  timed pass isn't paying page-fault and cold-cache costs.
- Use a monotonic high-resolution clock (std::chrono::steady_clock) and
  time many millions of accesses per sample, never individual accesses.
- Repeat each measurement 5-10 times; report the MINIMUM (least noise)
  or median, never a single run.
- Close other applications; on a laptop, run plugged in.
- Pin down variance: if two runs of the same config differ by >10%,
  something (thermal throttling, background load) is polluting results.

7. OPTIONAL EXTENSIONS
----------------------
- Measure write vs. read latency separately.
- Multi-threaded sweep: does per-core L1/L2 behave differently from
  shared L3 when several threads hammer memory at once?
- On Linux you could confirm findings with `perf stat -e cache-misses`;
  on macOS, Instruments (CPU Counters template) plays a similar role.

8. SUGGESTED OUTPUT
-------------------
Have the program print CSV lines: size_bytes,stride,ns_per_access.
Redirect to a file and plot it (e.g. with Python/matplotlib or a
spreadsheet). The plot is the deliverable — the cache structure should
be visible at a glance.
